# Friday Desktop Work —— Electron + Vue 3 远程工作流客户端 · 详细方案

> 版本 v1.0（2026-10-19 整理）
> 目标：用 Electron + Vue 3 做一个**纯客户端**的桌面工作流界面，连到远程机器上的 Friday（friday-server），
> 实时看它干什么（会话流、终端、文件、浏览器、子 Agent，全部卡片化）、随时插话、语音对话。

---

## 0. 结论摘要（一页看懂）

1. **不重复造协议**。桌面 Friday 项目已有一套完整的远程协议（`qt/docs/REMOTE.md`，JSON-RPC 2.0，"协议的唯一真相来源"），
   远程机器跑常驻服务 `friday-server`，客户端只是视图。本应用就是该协议的**第三个客户端**（Qt、Swift 之后），零服务端改动即可跑通绝大部分功能。
2. **连接（已定为「扫码一键连」）**：手机扫客户端二维码（SChat login-session，`SCSH:1:login:<token>`）→ 客户端列出 bot →
   点选指定的 Friday bot → 工作连接（`/connect` → `friday://pair` → `wss://`）与语音（WebRTC 打给 bot）全部自动建立。
   客户端里没有账号/密码/IP/端口/密钥输入。SSH（`ssh.exe` + `--attach` 桥）、WSL、手贴配对链接降为开发者后备（设置 › 高级）。
   代价是两处服务端小改（Friday 受信配对 + `/connect`）+ 一处 chatserver 建设（机器人通话），见 §4.0 与 §6.6。
3. **实时卡片**：消息流 + 工具卡片靠 `conversation.subscribe` + `message`/`message.patch` 增量事件（声明 `messagePatch` feature）；
   终端卡片 `term.*` + `term.output`（xterm.js）；文件卡片 `fs.list {files:true}` + `fs.read` 预览；
   浏览器卡片 `browser.watch` + `browser.frame`（JPEG 帧镜像 + `browser.input` 鼠键转发）；
   后台子 Agent 卡片 `team` 事件 + 运行记录块。全部会话动静总览用 `activity.subscribe`。
4. **语音是唯一有取舍的部分**：现协议没有实时音频流。三档方案——
   - **A 档**（零改动）：录音文件上传 + `assistant.say`，本机 TTS 播报，先跑通体验；
   - **B 档**（协议扩展）：给 friday-server 加 `voice.*`，音频帧走同一条 JSON-RPC 连接回传（纯客户端↔服务端闭环，但要改 C++）；
   - **D 档（SChat WebRTC，推荐）**：复用 Friday 助手已有的机器人通话管线（v2.3 已真机联调）+ Electron 的 Chromium 原生 WebRTC——
     **两边都不写媒体代码**，UDP+Opus 真实时（延迟最优），还顺带得到助手主动来电和视频通话。代价是要一套 chatserver + SChat 账号（见 §6.3）。
   建议：已有 SChat 部署/账号就 D 档为主、B 档做无 chatserver 时的对等备份、A 档做最终降级。
5. **工程**：Electron 44（当前稳定线）+ Vue 3 + TypeScript + Pinia + Vite（electron-vite 脚手架），
   xterm.js、ws、原生 ssh 子进程；electron-builder 出 Windows 安装包 + 便携 zip。
   主进程负责传输/协议/缓存，渲染进程纯 UI，contextBridge 隔离。
6. **里程碑**：M1 连接与会话流（核心打通）→ M2 四类实时卡片 → M3 语音（先 A 档后 B 档）→ M4 多机器/通知/自动安装升级。

## 2. 目标与范围

**要做的**

- 一个 Windows（后续可扩 macOS/Linux）桌面应用：连接远程机器上的 Friday，实时交互。
- 实时工作流卡片：会话消息流（含工具调用卡片）、终端、文件、浏览器、后台子 Agent、待确认审批。
- 语音对话：本机麦克风 → 远程 Friday → 语音流回放。
- 多台远程机器管理（添加、切换、连接状态）、助手时间线。
- 完整的断线重连、心跳、积压处理，长会话不卡。

**不做的（明确排除）**

- 不在 Electron 里跑 Agent/工具/MCP（那是远程 friday-server 的事）。
- 不做本地会话存储——一切以服务端为准，本地只留：机器列表、配对令牌、UI 偏好、媒体缓存。
- M1–M3 不动 Friday 仓库的代码（除了 M3-B 的 `voice.*` 服务端扩展，单独走 Friday 的分支/发布流程）。
- 不做手机端、不做中转/推送服务（协议 §10 已预留，将来再说）。

**进程职责划分原则**

- 主进程 = 所有网络与子进程 I/O、协议状态、磁盘缓存、安全边界；渲染进程 = 纯视图与本地音频 I/O。
- 渲染进程不接触：SSH 命令行、令牌明文（调用 `pair` 后由主进程保管）、远程文件原始字节之外的任何系统资源。
- IPC 用 `contextBridge` 暴露少量带类型的方法 + 事件订阅（`ipcRenderer.on` 封装成 `EventEmitter` 代理）；
  大块二进制（终端输出、浏览器帧、音频帧、媒体文件）用 `ArrayBuffer` 结构化克隆直传，避免 base64 双重拷贝。

## 4. 连接与通讯层设计

### 4.0 一键连接：扫码 + 选 bot（主入口，用户唯一要做的两个动作）

客户端里**没有**账号、密码、IP、端口、密钥任何输入。用户只做两件事：手机扫客户端显示的二维码、点选指定的 Friday bot；
之后工作连接（friday-server 完整协议）和语音通道（WebRTC）全部自动建立。

前置（一次性，与本项目无关的既有事实）：手机 SChat 账号与远程 Friday bot 是好友且是 owner（`assistant.channels.bindCode`
6 位绑定码绑定过）；远程机器跑着 friday-server（含助手）。

```
① 扫码登录（chatserver 现成，零改动；login_http.go）
   Electron: POST /login-sessions {deviceId, devicePlatform:"friday-work", deviceName}
     ← {token, expiresAt(5min), intervalMs}
   渲染二维码: SCSH:1:login:<token> ─────► 手机 SChat 扫码 → resolve（看到设备名/IP）→ 批准
   Electron: POST /login-sessions/poll {token, deviceId} 每 2s
     ← approved（一次性）: {userId, accessToken, refreshToken}（与 /auth/login 字节一致）
   WS wss://chatserver/ws 子协议 schat-ws.v1；hello {v:1, token, deviceId} → self
② 选 bot（现成；formatUser 带 isBot）
   getFriends → 过滤 isBot=true → 界面列出「我的机器人」→ 用户点选指定的 Friday bot
③ 工作通道（要加：Friday `/connect` + 受信配对，见 §6.6 缺口 #2 #3）
   Electron 经 WS 给 bot 发 "/connect"（客户端自动发，用户无感）
     → Friday 助手（owner-only）：进程内 pairDevice(trusted)（WS 入口没开就先开）
     ← bot 把 friday://pair?u&t&f&n 链接发回聊天（只显示一次）
   Electron 解析 → wss://u 连 friday-server（令牌+证书 SHA-256 指纹）→ hello → 完整协议
     受信设备：term.*/browser.* 解锁（现状 WS 配对设备一律错误 4，需加信任级别）
④ 语音通道（要加：chatserver 机器人通话，见 §6.6 缺口 #1；媒体面两边现成）
   点通话 → p2p_request {toUserId:bot, callType:"audio"} → bot 自动接
   → WebRTC P2P/TURN（Opus 48k）→ 实时对话（听写/大脑/合成回念全在远程 Friday）
```

安全模型：
- 扫码登录双因子（token + deviceId：拍屏照片不够用）、5 分钟过期、一次性领取、IP/用户限速（login_http.go 现成语义）
- `/connect` 只对 owner 生效；配对链接只显示一次，设备可 `--revoke` 吊销
- 已知取舍：bot 会话不 E2E（契约如此），配对链接经 chatserver 中转——自建 chatserver 的威胁模型里可接受；
  更严格时把 friday-server 的 WS 入口绑 LAN/Tailscale（REMOTE.md §8 本就建议）
- 全部令牌/凭据存 Electron 主进程 safeStorage；渲染进程拿不到明文（见 §3 职责划分）

SSH/WSL/手贴配对链接保留为开发者后备入口（设置 › 高级），普通用户永远见不到。

### 4.1 协议要点（对齐 REMOTE.md）

- **分帧**：SSH/WSL 字节流上每条消息一行紧凑 UTF-8 JSON + `\n`；WebSocket 一文本帧一条。
- **JSON-RPC 2.0**：请求带自增 `id`；回复按 `id` 对（顺序不保证）；服务端事件无 `id`（`method:"message"`）。
- **握手**：连上第一条必须是 `hello`：
  ```jsonc
  {"protocol":1,
   "client":{"name":"Friday Work","version":"0.1.0","platform":"windows","kind":"desktop"},
   "features":["messagePatch"]}
  ```
  回复带 `server`（版本/主机名/`host` 类型）+ `state` 全量快照（summaries/runner/team/engines/secrets/directories/terminals/browser）。
  `server.features` 决定可选功能（activity/tail/services/powers/loops/memory/…），没有的方法按 `-32601` 降级隐藏对应 UI。
  协议版本不符（错误 1）→ 提示并引导自动安装匹配版本（M4）。
- **状态同步**：事件带完整快照、可乱序覆盖；`message.patch`/partial `conversation` 例外（带版本，对不上就 `message.get` 整条）。
- **断线重连**：不补事件。重新 `hello` → 重新订阅打开的会话 / activity / assistant。
- **心跳与超时**：WS 客户端每 15 s ping、45 s 无回音断开重连；SSH 用 `ServerAliveInterval=15 ServerAliveCountMax=3`；
  请求超时按协议（hello 30 s、`file.*` 3 min、其余 60 s）。
- **只订看着的**：切走机器 / 切走会话时 `conversation.unsubscribe`，后台连接保持（侧边栏、审批、运行状态照常更新）。

### 4.2 SSH 传输（开发者后备，保留）

- 探测远程 shell（对齐协议 §2）：先跑 `echo FRIDAY-PROBE %OS% $env:OS`，按展开结果拼路径：
  - Linux/macOS：`~/.friday-server/bin/friday-server --attach`
  - Windows cmd：`"%USERPROFILE%\.friday-server\bin\friday-server.exe" --attach`
  - Windows PowerShell：`& "$env:USERPROFILE\.friday-server\bin\friday-server.exe" --attach`
  - WSL：`wsl.exe -d <发行版> --exec sh -c 'exec "$HOME/.friday-server/bin/friday-server" --attach'`
- 用 Node `child_process.spawn` 起系统 `ssh`（Windows 自带 OpenSSH 客户端）：
  `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 [-i 私钥] [-p 端口] user@host '<attach 命令>'`
  stdin/stdout 管道按行分帧；stderr 收集进连接日志（`bridgeError` 事件只由桥发，注意区分）。
- 登录方式：密钥（默认，ssh-agent/`~/.ssh`）、指定私钥文件（`-i` + `IdentitiesOnly=yes`）；
  **密码方式 M4 再做**（一次性 SSH_ASKPASS 脚本装公钥，对齐 Qt 客户端 §11，不保存密码）。
- 失败语义：退出码 255 = ssh 自己连不上（网络/认证），显示人话原因（对齐 `RemoteTarget::sshFailureReason` 的文案思路）；
  未 hello 就断且没说过协议 = 服务端没装 → 走自动安装（M4）。

### 4.3 WebSocket + 设备配对（M1）

- 入口在远程机器上开启（`friday server --websocket on`，或经 SSH 连接时 `server.websocket` 方法开）。
- 添加机器支持三种输入：`user@host[:port]`、`wsl:发行版`、配对链接 `friday://pair?u=&t=&f=&n=`（或直接 `wss://…`）。
- 配对（对齐 §8）：经 SSH 连接调 `server.pair {name, host?}` → 拿 `{deviceID, token, urls, secure, fingerprint, link}`；
  令牌 + 指纹存 `userData/Remotes/pairings.json`（仅当前用户可读写）。链接可展示为二维码（M4 加，方便手机）。
- TLS 校验：不认 CA，只认配对时记下的证书 SHA-256 指纹。Node 侧实现：`ws` + 自定义 `agent`
  （`checkServerIdentity: () => undefined` 关掉默认校验），upgrade 完成后用 `socket.getPeerCertificate().fingerprint256` 比对，
  对不上立即断开并提示"证书变了，需要重新配对"。
- hello 必须带 `token`；错误 5（未配对/吊销）→ 不自动重连，提示重新配对。

### 4.4 连接生命周期

```
空闲 → 连接中（探测/建流）→ 握手(hello) → 就绪(快照落地, 按需订阅)
  ↑                                      │
  └──── 断线（重连退避 1s/2s/5s/…上限 60s，配对失效则停）←──┘
```

- 每台远程机器一个独立的连接对象（多机器并行、后台常连）；同一时间只"看着"一台。
- 请求表：`id → {resolve, reject, timer}`；重连时全部未决请求以"连接断开"拒绝。
- 写缓冲节流：协议已设计服务端侧积压（>256 KB 暂停推送），客户端侧我们发送量小，不需要额外机制。

- 停靠卡片沿用 Friday 桌面端的交互模型（TERMINAL.md §2：四边停靠、拖拽分组、最大化/收起、布局按会话存），
  M2 先做右侧一列 + 最大化/收起，完整拖拽停靠 M4 再补。
- 深浅色跟随系统；中文 UI。

### 5.2 会话列表与活动总览

- 侧边栏会话树：`summaries` 事件（按 `updatedAt` 排序、置顶分组、目录分组、待确认橙点、生成中动画）。
  新建会话（`conversation.create`，带本地"上次选的"权限模式/思考档位）、改名/置顶/删除、全文搜索（`conversation.search`）。
- **活动总览卡**（`server.features` 有 `activity` 时）：订阅 `activity.subscribe`，
  列出全部会话的 `SessionActivity`（状态 idle/running/approval/question/quota/error、任务目标与步骤、最近简报、待确认项），
  `ActivityEvent` 实时更新（不合批、一到就转）。这是"实时看远程 Friday 都在干什么"的第一入口；
  点一条 = 切到那段会话。助手时间线同理（`assistant.subscribe` → `assistant.entry/board/state/push` 事件）。

### 5.3 消息流与工具卡片（M1 核心）

- 数据源：`conversation.subscribe` → `conversation`（结构，nodes + selectedChildren 构成消息树/分支）、
  `message` / `message.patch`（内容，流式合并）、`runtime`（排队/审批/可否发送/生效引擎）。
- **消息树与分叉**：按 `parentID` + `selectedChildren` 渲染当前路径；节点有多个孩子时显示分支切换器（`runner.selectBranch`）。
- **块渲染**（对齐 ARCHITECTURE.md §5.3）：
  | 块 | 卡片样子 |
  |---|---|
  | text | Markdown 渲染（流式增量追加；停在底部时跟随） |
  | thinking | 可折叠"思考"块，浅色斜体 |
  | tool | **工具卡片**：symbol 图标 + 标题 + 状态徽标（排队/运行中/确认中/完成/失败）+ 参数摘要一行 + 结果摘要；展开看完整参数/结果/transcript（子 Agent 的运行记录块递归渲染成嵌套卡片流） |
  | media | 缩略图/播放器；附件经 `file.read {media: relativePath}` 分块拉取 + 磁盘缓存（按 会话ID/相对路径），第二次直接本地读 |
- **审批**：`runtime.pendingApproval` → 橙色横幅列出待确认调用（工具名/标题/参数），批准/拒绝（`runner.resolveApproval {eventID, approved}`）；
  `ask_user` 的问题卡片支持选项点选 + 补充回答（`answer.answers/reply`）。切到别的机器也有橙点 + 系统通知（`attention` 事件）。
- **输入框**：发送（`runner.submit`）、停止（`runner.stop`）、排队的消息（增删/继续 `runner.removeQueued/resumeQueue`）、
  附件（本地文件 → `file.upload` 分块 1 MB 上传 → `attachments:[服务端路径]`）、
  模型/思考档位/权限模式/工作目录（`runner.setEngine/setThinking/setPermissionMode/setWorkingDirectory`，目录用 `fs.list` 浏览远程目录）。
- **用量与速度**：`stats`（tokens/s、上下文）显示在助手消息底部。

### 5.4 终端卡片（M2）

- 打开：`term.open {id, conversationID, cols, rows, workingDirectory?}`（cols/rows 由 xterm + fit 插件量出）；
  接上已有终端：`term.attach` → 回 `{data(base64 最近输出 ≤512 KB), cols, rows}` → 清屏后按该尺寸重放再按本地尺寸 `term.resize`。
- 输出：`term.output {id, data(base64)}` 事件（原始字节、不合并、马上转）→ `term.write(Uint8Array)`（xterm 直接吃 UTF-8 字节流）。
- 输入：xterm `onData`（已经过终端键位编码，含 IME/粘贴）→ base64 → `term.write`。
- 标签页：`terminals` 状态（TerminalsState）列出这台全部终端（各会话的），Agent 用 `run_in_terminal` 开的一出现就选中并自动打开卡片。
- 远程终端跑 `htop/vim` 等全屏程序天然可用（libvterm 在服务端，客户端只是字节流镜像）。
- **限制**：WebSocket 配对连接 `available:false`——卡片显示原因（"终端就是那台机器上的 shell，只有 SSH/WSL 连接可用"）。

### 5.5 文件卡片（M2）

- 目录树：`fs.list {path, hidden?}`（v2.12 起带 `files:true` 连文件一起列；`roots` 给主目录和各盘）。
- 预览：`fs.read {path, offset, length}` 每次最多 1 MB 分块拉 → 文本（代码高亮，行号）、图片（base64 → blob URL）、
  其他类型显示图标+大小+"在这台机器上"提示。**只读**——协议没有客户端写文件的方法（设计如此：客户端只是视图）。
- **"让 Friday 改"**：预览工具栏的编辑按钮 = 预填一条消息发到当前会话（引用文件路径 + 行号范围），由远程 Agent 用 `edit_file` 改——
  修改过程实时出现在消息流的工具卡片里（这正符合"文件编辑实时以卡片展示"的要求：展示的是 Agent 的编辑动作）。
- 工作目录选择器复用同一组件（只列目录模式）。

### 5.6 浏览器卡片（M2，`server.features` 有 browser 时）

- 标签列表：`browser` 状态事件（BrowserState：tabs 的标题/网址/加载状态/视口/对话框/handOver）。
- 画面：`browser.watch {tab, width, height}`（按卡片 CSS 尺寸）→ `browser.frame {tab, data(jpeg base64), viewport}`（变了才推、积压丢帧只要最新）→ `<img>`/`<canvas>` 绘制。
- **输入转发**：卡片上捕获鼠标（move/press/release/wheel + 修饰键）和键盘（keydown/keyup 的 key/code/text），
  按 BROWSER.md §9 的 `browser.input` 结构编码发送（`modifiers` 用 Qt KeyboardModifiers 数值映射表）；
  输入法提交的文字走 `{kind:"text"}`。输入期间"算用户在动，智能体让开"——正好实现"人机共驾同一个页面"。
- 卡片尺寸变化 → `browser.container {tab, width, height}`；智能体定了固定视口时显示"固定视口"标记，`browser.fit` 恢复跟随。
- 对话框（alert/confirm）：网页弹框按 `browser.dialog {accept, text?}` 回答；`browser.handOver` 事件 → 打开对应会话的浏览器卡片并高亮"请你操作"，操作完 `browser.handOverDone`。
- 同终端：WebSocket 配对连接不可用（`available:false` + 原因），卡片降级为说明。

### 5.7 后台子 Agent 卡片（M2）

- `team` 事件（TeamState.runs）：每个子 Agent 一张行卡片——名字、活动（kind: tool/waitingApproval/…标题）、步数、运行时长、速度、排队消息、停止/插话（`agent.stop` / `agent.send`）。
- 消息流里的子 Agent 工具卡片：`transcript`（运行记录块）递归渲染，`message.patch` 的 `tools` 补丁让每步实时刷新——
  这是"实时看 Friday 操作的内容"的主舞台（它 read_file 我就看到它读了什么、它 edit_file 我就看到改了哪几行、它跑命令我就看到输出）。
- 等确认的子 Agent 调用不管嵌几层都顶上来（`pendingApproval` 橙标）。

## 6. 语音方案（重点）

> 需求原文：通过 Electron 的麦克风获取内容发给远程 Friday，然后获取语音流播放出来。
> 现状：REMOTE.md **没有**实时音频流方法（Qt 桌面端的语音模式是"本机收音 + 本机 friday-voice Power"，不走协议）。
> 所以语音分两档：A 档零服务端改动先跑通体验；B 档做协议扩展拿到真正的低延迟语音流（推荐最终形态）。

### 6.1 A 档 · 录音消息 + 客户端播报（M3-A，零服务端改动）

```
按住说话 ──getUserMedia+MediaRecorder(webm/opus)──► 一段录音(≤60s)
        ──file.upload 分块上传──► 远程路径
        ──assistant.say {text:"", attachments:[路径], source:"voice"}──► 助手
        ◄── assistant.entry 事件（流式文字回复，journal 时间线）
        ── speechSynthesis(Web Speech API) 逐句朗读回复 ─► 本机扬声器
```

- 识别/理解发生在远程（助手按"语音消息"处理：先听写再交大脑，ASSISTANT.md §8 的既有链路；
  **风险点**：`assistant.say` 的附件是否自动走听写要在 M1 连上真机实测确认，不行就降级为 B 档提前）。
- 播报用系统 TTS（Windows SAPI 语音），质量一般但零依赖；打断 = cancel()。
- 优点：一周内可用；缺点：非流式、延迟高（整段录完才发）、回放不是 Friday 的声音。

### 6.2 B 档 · 协议扩展 `voice.*`（M3-B，推荐；需改 friday-server，按 Friday 仓库流程）

**目标形态**（复刻 Qt 语音模式，只是音频 I/O 跨网络）：

```
 Electron 渲染进程                       远程 friday-server
 ┌──────────────┐   voice.feed(PCM16 帧) ┌──────────────────────────────┐
 │ getUserMedia │ ─────────────────────► │ RemoteVoiceSession            │
 │ +AudioWorklet│                        │  ├ RealtimeTranscriber        │ ← friday-voice:
 │ (AEC/NS 打开) │ ◄── voice.audio 帧 ────│  │  (流式听写+VAD+声纹)        │    流式 ASR/TTS
 │              │                        │  ├ 定稿 → AssistantRuntime    │
 │ WebAudio 播放 │ ◄── voice.state ────── │  │   .say(source=voice)       │    大脑(在线模型)
 │ (队列+打断丢弃)│ ◄── voice.clearAudio ──│  └ RealtimeSpeaker            │
 └──────────────┘                        │     (边写边读,逐句合成)        │ ← 复用 AssistantVoice
                                         └──────────────────────────────┘    的打断/回声/说完判断
```

**协议草案**（写进 REMOTE.md §6 新小节「语音」，`server.features` 加 `"voice"`，不改 protocol 版本）：

| 方向 | 方法/事件 | 参数 | 说明 |
|---|---|---|---|
| C→S | `voice.start` | `{inputSampleRate, outputSampleRate, conversationID?}` | 开一次语音会话；不带 conversationID = 助手模式（`say source=voice`），带 = 对着某段会话说（`runner.submit`） |
| C→S | `voice.feed` | `{data(base64, PCM16 小端单声道), seq}` | 40–100 ms 一帧；seq 乱序丢弃并回 `voice.resync` |
| C→S | `voice.setPlaying` | `{playing}` | 客户端播完了才续（对齐 AssistantVoice::setPlaying，念的时候也听用） |
| C→S | `voice.interrupt` | `{}` | 用户点停：不念了、不想了（clearAudio + 取消） |
| C→S | `voice.stop` | `{}` | 结束 |
| S→C | `voice.state` | `{state: off/starting/listening/hearing/thinking/speaking, caption?, pending?}` | 状态机 + 实时字幕（正在听的这句/攒着没交的） |
| S→C | `voice.audio` | `{data(base64 PCM16), sampleRate}` | 合成音频帧（边写边读逐句下发） |
| S→C | `voice.clearAudio` | `{}` | 打断：客户端丢弃播放队列 |
| S→C | `voice.error` | `{message}` | 如远程没装本地语音 Power |

- **带宽**：16 kHz × 16 bit × 单声道 ≈ 32 KB/s（base64 后 ~43 KB/s）。局域网 SSH/WS 完全可承受；
  跨公网 M4 可选 Opus 编码（`MediaRecorder audio/webm;codecs=opus` → 服务端 ffmpeg 解码，服务端已有解 webm 的路径）。
- **回声**：Electron 用 Chromium 的 AEC（`getUserMedia({audio:{echoCancellation:true, noiseSuppression:true}})`）+
  服务端既有的文本回声比对（`AssistantVoice::isEcho`）双保险；文档建议戴耳机。
- **服务端改动点**（Friday 仓库，估算 300–500 行 C++）：
  - `qt/src/core/remote/RemoteServer.cpp`：`voice.*` 方法分发 + 会话对象（每个客户端最多一个）；
  - 从 `AssistantVoice` 抽一个无音频设备的 `VoicePipeline`（现有逻辑：喂 PCM→听写→定稿→say→边写边读→PCM 出），
    Qt 桌面端的 VoiceMode 和 RemoteVoiceSession 都调它；
  - 先改 `qt/docs/REMOTE.md`（协议唯一真相来源），feature 名 `voice`，向后兼容（旧服务端 `-32601` → 客户端显示"远程要升级到 vX.Y 才能语音"）；
  - 按 CLAUDE.md 约定执行：**先切 main 拉取远程最新 → 新功能开 `vX.Y` 分支 → 中文提交、不加 AI 署名 → 不自行 push**（push/合并/发版由用户拍板）。

### 6.3 D 档 · SChat WebRTC 通话（推荐主路线；Friday 零改动 + Electron 零媒体代码）

**思路**：Friday 助手的机器人通话（v2.3）本来就是 SChat 体系里的 WebRTC 通话——机器人接主人打来的电话，
听写→大脑→逐句合成回念的整条管线已在远程机器上跑通（真机联调过，`qt/src/core/assistant/calls/` + `qt/vendor/schat-call`）。
Electron 里 Chromium 自带完整 WebRTC 栈（iOS/安卓的 SChat 客户端用的就是它）。**让 Electron 扮演 SChat 的一个用户端，
打普通电话给 Friday 机器人**——媒体面 P2P 直连，两边各自零媒体开发。

```
Electron 渲染进程（Chromium WebRTC）                     远程机器上的 Friday 助手
┌────────────────────────────┐                        ┌──────────────────────────────┐
│ getUserMedia(音频, AEC/NS)   │    ⑥ SRTP/Opus 48kHz    │ AssistantCalls（v2.3 已有）    │
│ RTCPeerConnection ──────────┼─────── P2P / TURN ─────►│ 48k→16k → VoiceActivity(VAD)  │
│ （编解码/抖动缓冲/播放全内置） │ ◄──────────────────────┼─ 听写 → say(source="call:schat")│
└──────┬─────────────────────┘                        │ 大脑 → 逐句合成 → Opus 回念     │
       │ ① REST /auth/login（或扫码）拿 device token      │ （只接主人打来的；自动接应一声；  │
       │ ② WS ws(s)://chatserver/ws                    │   打断=v2.5 语义；声纹过滤）     │
       │   子协议 schat-ws.v1，hello {v,token,deviceId}   └──────┬───────────────────────┘
       │ ③ p2p_request {toUserId:botId, callType:audio}        │ botToken hello（另一条信令 WS）
       │ ④ p2p_signaling: offer/answer/ice_candidate           │ + /bot/v1/getIceServers（TURN）
       ▼ ⑤ p2p_glare / hangup                                 │ libdatachannel+Opus（已编进内核）
┌────────────────────────────────────────────────────────────────┐
│ chatserver（信令中继，自建 Go 服务，用户有全部源码；自签 TLS 按 SPKI 指纹认）│
└────────────────────────────────────────────────────────────────┘
```

**Electron 端要实现的**（比预想少，全部是应用层）：

| 部分 | 内容 | 量级 |
|---|---|---|
| 账号 | `/auth/register`/`/auth/login`（或 `/login-sessions` 手机扫码授权）拿 device token，存本机密钥库；一个 SChat 用户 + 加 Friday 机器人为好友（或经 `assistant.channels.add` 的 `owners` 预绑成主人） | 小 |
| 信令 | `schat-ws.v1` 最小子集：hello/ping + `p2p_request`/`p2p_response`/`p2p_signaling`/`p2p_glare`/hangup；envelope `{e,t,a,d}` 文本帧 JSON（和 friday 协议一样好写）；ICE 用公共 STUN + 对端回的候选（机器人那边已带 TURN） | ~几百行 TS |
| 媒体 | **零代码**：Chromium 的 Opus 编解码、抖动缓冲、NetEQ、AEC/NS/AGC、自动播控全部内置；`RTCPeerConnection` 收到的轨道直接 `<audio>` 播放 | 0 |
| UI | 拨号盘/通话中界面（时长、音量波形、静音、挂断）+ 接助手主动来电 | 小 |

**工作台的整合**（两条通道在助手时间线汇合）：语音走 SChat、工作流走 friday-server（SSH/WS）并行；
`assistant.subscribe` 的时间线上实时看到「Electron 打来语音电话」「通话结束 · 3 分 05 秒」，通话里说的话、
助手的回复逐条出现在 journal——工作台不用自己同步通话状态。

**前提条件（2026-10-19 已把两个仓库更新到最新并审计，结论见 §6.6）**：

1. **chatserver 要补机器人通话支持**（缺口 #1）：`setCallSettings`/`getIceServers`/botToken hello 在 Secret-Chat 仓库的
   **所有分支、全部历史里都不存在**（pickaxe 为空）——不存在「升个级就有」的版本，
   要按 Friday `SChatChannel` 已实现的客户端行为反推契约自建（约 300–500 行 Go + 测试）。
2. 部署一套 chatserver（Go 单服务，源码全有；放远程机器或任一常开服务器）+ 可选 coturn（跨 NAT 时才有必要；
   同局域网 host 候选直连即可）。`/bot/v1/getIceServers` 发 TURN 临时凭据的机制随 #1 一起建。
3. 远程 Friday：助手开着 + 配 SChat 渠道（`assistant.channels.add {kind:"schat", options:{server,pin}, token, owners:[…]}`）
   + 语音能力（本地 friday-voice Power，或在线 ASR/TTS 服务）。
4. 手机 SChat 账号与机器人好友/主人关系（`assistant.channels.bindCode` 6 位绑定码即可，一次性；也是扫码登录的前提）。

**限制**：语音进的是**助手的**对话（`source="call:schat"`），不能直接对着某段工作会话说（B 档可以带 conversationID）——

通话状态机在服务端，Electron 只是又一个「主人设备」。

**白送的**（同一信令已实现）：助手主动打来（`call_user`，经 chatserver 信令 + VoIP 推送语义）、视频通话
（Friday 发 CallAvatar 光环画面，Electron 加摄像头即可双向）、P2P 文字会话（`p2p-text` DataChannel，`AssistantTextSession`）。

## 8. 数据模型（TS 类型，对齐存档格式）

数据格式 = `conversations.json` 的规则（ARCHITECTURE.md §5.2/§5.3）：UUID 大写带连字符字符串、日期 ISO 8601 UTC 无毫秒、
可选字段无值不写键、枚举原始字符串。协议对象直接建类型：

```ts
interface Conversation { id: Uuid; title: string; createdAt: Iso; updatedAt: Iso;
  nodes: ChatMessage[]; selectedChildren: Record<Uuid, Uuid>; engineID?: Uuid;
  workingDirectory?: string; permissionMode: 'auto'|'plan'|'full'; thinking?: Level; pinned: boolean }
interface ChatMessage { id: Uuid; role: 'user'|'assistant'; blocks: MessageBlock[]; createdAt: Iso;
  stats?: GenerationStats; error?: string; notice?: string; parentID?: Uuid; taskNote?: string; folded?: boolean }
type MessageBlock = { id: Uuid; text: string } | { id: Uuid; thinking: string }
                   | { id: Uuid; tool: ToolEvent } | { id: Uuid; media: MediaAttachment }
interface ToolEvent { id: Uuid; name: string; arguments: JsonObject; status: string;
  result: string; title?: string; symbol?: string; preview?: ...; media?: ...;
  transcript?: MessageBlock[]; agentName?: string; queued?: boolean; modelResult?: string }
// + Summary / RunnerState / Runtime / TeamState(Run) / EnginesState / DirectoriesState /
//   TerminalsState / BrowserState(tab) / SessionActivity / ActivityEvent / TurnBrief /
//   AssistantState / JournalEntry / Board / Channel / PowersState / ModelsState …
```

messagePatch 的补丁结构（`{base, version, fields?, blocks?: {ids?, set?, tools?}}`）单独建类型，
应用失败（缺块/版本断）自动 `message.get` 整条——照协议写，不猜。

## 9. 安全设计

- `contextIsolation: true`、`nodeIntegration: false`、CSP 收紧；渲染进程不接触 Node。
- 配对令牌/指纹只存主进程管理的 `userData`（Windows 依赖用户目录 ACL）；不经渲染进程、不进日志。
- SSH 走系统 ssh：不实现密码缓存（密码流程仅 M4 的一次性装公钥，用完即弃，对齐 Qt 做法）。
- 审批语义照搬协议：工具执行都在远程、按那段会话的权限模式确认；客户端只是确认的入口之一。
- 浏览器卡片输入都算"用户操作"（协议定义），不会绕过智能体的审批；`handOver` 的页面需要用户亲手做的部分只提示、不代点。
- 上传/下载都过协议（`file.upload` / `file.read`），不暴露任意路径读本机文件的 IPC。

| 风险 | 影响 | 对策 |
