# 客户端设备：让服务端用上客户端机器连的硬件（device.* 协议草案 v1）

> 状态：**草案**，客户端（friday-desktop-work）已按本文实现；服务端（friday-server）待对接。
> 定稿后并入 `Friday/qt/docs/REMOTE.md`（唯一真相来源），错误码以那边分配为准。

## 1. 要解决什么

服务端（Agent 和它跑的程序）在远端，硬件插在客户端这台机器上：ESP32 之类的开发板（USB 串口）、摄像头。
目标是**服务端能像用本机设备一样用它们**，而且：

- 不装驱动、不加原生模块（Electron 自带 WebSerial / getUserMedia）；
- 走现有的 WebRTC 工作通道，不另开端口、不要求两边互通；
- 每个设备由客户端上的人**明确授权**，服务端只能碰被共享的设备。

| 设备 | 服务端怎么用 | 底层 |
|---|---|---|
| 串口（ESP / Arduino / 任意 USB 转串口） | `rfc2217://127.0.0.1:<port>` —— esptool、pyserial、PlatformIO、idf.py 原生支持 | 反向 RPC 开会话 + 一条专用 DataChannel 跑 RFC 2217 |
| ESP 烧录 | Agent 工具 `client.esp.flash`：把固件发给客户端，客户端本机烧 | esptool-js（Espressif 官方网页烧录器同款），本机速度 |
| 摄像头 | Agent 工具 `client.camera.snapshot`：拍一张 JPEG 回来 | getUserMedia → canvas |

为什么串口不用 pty：esptool 烧录要拉 DTR/RTS 让芯片复位进下载模式，烧录中途还要改波特率；pty 只传字节，
这两样都传不过去。RFC 2217（Telnet COM-PORT-OPTION）把波特率、DTR/RTS、清缓冲都带在流里，
而且 pyserial 系的工具原生支持 `rfc2217://`。

为什么烧录默认放客户端：隔着公网走 RFC 2217 烧录，每个块都要一个来回，走 TURN 时又慢又容易握手超时；
esptool-js 在本机直接烧，跟插在本机上一样快。RFC 2217 烧录仍然可用（服务端自己跑 esptool 的场景）。

## 2. 能力声明（hello）

客户端在 `hello` 里声明自己能接设备请求；**没声明的客户端，服务端不得发 `device.*` 请求**。

```jsonc
{
  "method": "hello",
  "params": {
    "protocol": 1,
    "client": { "name": "Friday Work", "version": "0.5.83", "platform": "windows", "kind": "desktop" },
    "features": ["messagePatch", "clientDevices"],
    "clientDevices": { "version": 1, "kinds": ["serial", "esp.flash", "camera"] }
  }
}
```

`kinds` 是客户端这次支持的能力；服务端只把对应的 Agent 工具挂出来。

## 3. 反向请求（服务端 → 客户端）

在同一条 `friday-work` DataChannel 上，**服务端也可以发请求**，客户端回响应，标准 JSON-RPC 2.0：

```jsonc
// 服务端 → 客户端
{ "jsonrpc": "2.0", "id": "s:17", "method": "device.list", "params": {} }
// 客户端 → 服务端
{ "jsonrpc": "2.0", "id": "s:17", "result": { "devices": [ ... ] } }
```

- `id` 由服务端分配，两个方向的 id 各管各的（建议服务端用字符串 `"s:<n>"`，日志里一眼分得清）。
  客户端原样回传，数字和字符串都接受。
- 客户端只认 `device.` 开头的方法，其余回 `-32601`。
- 大消息照旧走 WorkFramer 分片（REMOTE.md §2），单条上限 64 MB；烧录固件、照片都直接放在 JSON 里（base64）。
- 客户端也会发**通知**（没有 `id`）：`device.changed`、`device.serial.closed`、`device.esp.progress`，见下文。

### 3.1 错误码（提案，待 REMOTE.md 分配）

| code | 含义 |
|---|---|
| `-32601` | 不认识的方法 |
| `-32602` | 参数不对 |
| `20` | 用户拒绝（或授权弹窗 60 秒没人理） |
| `21` | 设备不存在 / 已拔掉 |
| `22` | 设备忙（已被别的会话或烧录占用） |
| `23` | 设备操作失败（打开失败、烧录失败、摄像头取不到画面……，`message` 里有原因） |

### 3.2 超时建议（服务端侧）

- `device.list`：10 秒
- `device.serial.open` / `device.camera.snapshot`：**90 秒**（含等人点授权最多 60 秒）
- `device.esp.flash`：**10 分钟**（4 MB 固件在 115200 下也能烧完；进度靠通知看）
- 其余 30 秒

## 4. 授权

客户端第一次收到某台机器对某个设备的请求时弹窗：**允许这次 / 始终允许 / 拒绝**。

- 「始终允许」按 *（机器, 设备, 能力）* 记在客户端，可在客户端撤销；「这次」只管这一个请求
  （串口是这一个会话）。
- 60 秒没人点 = 拒绝（`20`）。
- `device.list` 不弹窗（只有设备名，不碰设备）。
- 使用中的设备在客户端界面上常亮提示，人可以随时断开（服务端收到 `device.serial.closed`）。

## 5. 方法

### 5.1 `device.list`

```jsonc
// params: {}
// result:
{
  "devices": [
    {
      "id": "serial:4292:60000:0",       // 不透明字符串，原样回传给其他方法
      "kind": "serial",
      "label": "COM5 · CP210x",
      "portName": "COM5",                // 拿得到才有
      "usbVendorId": 4292, "usbProductId": 60000,
      "espHint": true                    // 常见 ESP 开发板桥芯片 / ESP 原生 USB，供 Agent 参考
    },
    {
      "id": "camera:3f1c…",
      "kind": "camera",
      "label": "Integrated Webcam"
    }
  ]
}
```

设备增减时客户端发通知 `device.changed`（params 为空，服务端要的话重新 `device.list`）。

### 5.2 串口：`device.serial.open` / `device.serial.close`

```jsonc
// device.serial.open params
{
  "deviceId": "serial:4292:60000:0",
  "mode": "rfc2217",        // "rfc2217"（默认）| "raw"
  "baudRate": 115200,       // 初始波特率（rfc2217 模式下之后可由流里的 SET-BAUDRATE 改）
  "dataBits": 8, "parity": "none", "stopBits": 1   // 可选
}
// result（DataChannel 已经 open 之后才回）
{ "sessionId": "k3v9x2", "channel": "friday-serial:k3v9x2" }

// device.serial.close params
{ "sessionId": "k3v9x2" }
// result: {}
```

流程：

1. 客户端授权 → 打开串口 → 在**同一个 RTCPeerConnection** 上 `createDataChannel("friday-serial:<sessionId>", { ordered: true })`
   （带内 DCEP，不用重新协商 SDP）。
2. 服务端在 `ondatachannel` 里按 label 认领；label 可能比 `open` 的响应先到，服务端先按 label 暂存。
3. DataChannel 上**全是二进制消息**，内容是字节流：
   - `rfc2217` 模式：RFC 2217 的 Telnet 流（客户端是 RFC 2217 *服务器*，IAC 0xFF 双写转义）；
   - `raw` 模式：串口原始字节，不转义、没有控制（给服务端桥到 pty 这类只要字节的用法）。
4. 任意一边关 DataChannel = 会话结束、串口释放。客户端结束时（人点断开、设备拔掉、被烧录接管失败）
   会先发通知 `device.serial.closed { sessionId, reason }`。
5. 同一个串口同时只能有一个会话（第二个 `open` 回 `22`）。

客户端实现的 RFC 2217 子集（够 pyserial / esptool / PlatformIO 用）：

| 选项 / 命令 | 处理 |
|---|---|
| Telnet `BINARY`、`SGA`、`COM-PORT-OPTION(44)` | 双向同意；其他选项一律拒绝 |
| `SIGNATURE(0)` | 回 `Friday Work` |
| `SET-BAUDRATE(1)` | 关串口按新波特率重开（WebSerial 不能热改），回实际值；0 = 查询 |
| `SET-DATASIZE(2)` / `SET-PARITY(3)` / `SET-STOPSIZE(4)` | 支持 7/8 位、无/奇/偶校验、1/2 停止位；不支持的回当前值（pyserial 会报错） |
| `SET-CONTROL(5)` | DTR on/off（8/9）、RTS on/off（11/12）、BREAK on/off（5/6）、无流控（1）、硬件流控（3）；查询（0/4/7/10）回当前值 |
| `NOTIFY-MODEMSTATE(7)` | 回 CTS/DSR/RI/CD 当前状态 |
| `SET-LINESTATE-MASK(10)` / `SET-MODEMSTATE-MASK(11)` | 回显确认 |
| `PURGE-DATA(12)` | 回显确认（客户端侧没有可清的缓冲） |
| `FLOWCONTROL-SUSPEND/RESUME(8/9)` | 暂停 / 恢复往通道里送串口数据 |

控制命令和数据**严格按流里的顺序**执行（复位时序靠这个）。

### 5.3 ESP 烧录：`device.esp.flash`

```jsonc
// params
{
  "deviceId": "serial:4292:60000:0",
  "files": [
    { "address": "0x0",     "data": "<base64>" },   // address 可以是数字或 "0x…" 字符串
    { "address": "0x8000",  "data": "<base64>" },
    { "address": "0x10000", "data": "<base64>" }
  ],
  "baudRate": 460800,       // 烧录波特率，默认 460800；ROM 握手固定 115200
  "flashMode": "keep", "flashFreq": "keep", "flashSize": "keep",   // 同 esptool，默认 keep
  "eraseAll": false,
  "compress": true,
  "before": "default_reset",  // default_reset | usb_reset | no_reset | no_reset_no_sync
  "after": "hard_reset"       // hard_reset | soft_reset | no_reset | no_reset_stub
}
// result
{
  "chip": "ESP32-S3 (QFN56) (revision v0.2)",
  "files": [ { "address": 65536, "size": 912384, "md5": "…" } ],
  "elapsedMs": 9234,
  "log": "…esptool-js 的输出（截尾 8 KB）…"
}
```

- 进度通知：`device.esp.progress { requestId, fileIndex, written, total }`（`requestId` = 这次请求的 `id`），最多每 250 ms 一条。
- 每个文件烧完都做 flash MD5 校验，对不上回 `23`。
- 这个口上**开着串口会话时**：客户端先把会话挂起（串口让给烧录，DataChannel 不关），烧完按原波特率和
  DTR/RTS 重新打开、继续转发——服务端的串口监视能直接看到新固件的启动日志。

### 5.4 ESP 信息：`device.esp.info`

```jsonc
// params: { "deviceId": "...", "before": "default_reset" }
// result: { "chip": "ESP32-S3 (QFN56) (revision v0.2)", "features": "WiFi, BLE, …", "mac": "f4:12:fa:…", "flashSize": "8MB" }
```

读完按 `hard_reset` 复位回应用。和烧录一样会临时接管开着的串口会话。

### 5.5 摄像头：`device.camera.snapshot`

```jsonc
// params（都可选）
{ "deviceId": "camera:3f1c…", "width": 1280, "height": 720, "format": "jpeg", "quality": 0.85, "warmupMs": 600 }
// result
{ "mime": "image/jpeg", "data": "<base64>", "width": 1280, "height": 720, "deviceId": "camera:3f1c…", "label": "Integrated Webcam", "takenAt": "2026-10-23T08:00:00Z" }
```

- 不给 `deviceId` 用默认摄像头；`width/height` 是期望值，实际以返回为准。
- `warmupMs`：开摄像头后等多久再拍（自动曝光要几百毫秒稳定），默认 600，上限 5000。

## 6. 服务端要做的（对接清单）

1. **反向请求**：RemoteSession 能往 work 通道发带 `id` 的请求并配对响应；只对声明了 `clientDevices` 的连接发。
2. **ondatachannel**：认领 `friday-serial:*`，按 sessionId 和 `device.serial.open` 的响应对上。
3. **串口桥（RFC 2217）**：Agent 工具（或命令）「把客户端的 <设备> 开在本机 <端口>」→ 在 `127.0.0.1:<port>`
   监听 → 每来一个 TCP 连接调一次 `device.serial.open(mode: rfc2217)` → TCP ⇆ DataChannel **原样搬字节**
   （服务端不用懂 RFC 2217，客户端才是 RFC 2217 服务器）→ 任一边断开就关另一边。
   - 用法：`esptool --port rfc2217://127.0.0.1:4000 chip_id`、`pio run -t upload --upload-port rfc2217://127.0.0.1:4000`、
     `python -m serial.tools.miniterm rfc2217://127.0.0.1:4000 115200`。
4. **Agent 工具**（建议命名，参数即上面的 params）：
   - `client.devices.list`
   - `client.serial.expose { deviceId, port? }` → 回 `rfc2217://127.0.0.1:<port>`；`client.serial.unexpose`
   - `client.esp.flash { deviceId, files: [{ address, path }] , … }` —— 服务端读本机文件转 base64 再调 `device.esp.flash`
   - `client.esp.info { deviceId }`
   - `client.camera.snapshot { … }` —— 结果存成服务端临时文件、当图片给模型看
5. **断线**：工作通道一断，所有 `friday-serial:*` 通道随 PeerConnection 一起没了；服务端关掉对应的 TCP 连接，
   重连后由使用方重新 `open`。

## 7. 安全

- 服务端只能拿到客户端上的人授权过的设备；授权按机器分开记。
- 摄像头每次拍照都是一次独立请求，「这次」授权只管这一张。
- 客户端界面常亮「设备使用中」，可一键断开；「始终允许」在设置里能撤销。
- 烧录和 RFC 2217 只对串口设备生效，不涉及任何本机文件读写。
